Cycle of a change

  1. Spec. The spec-writer writes the change in openspec/changes/<id>/ (proposal, specs, tasks) and critiques it with the grilling skill: the decisions only the developer can make (D-<n>) go to them in rounds, through the orchestrator. With no open decision, the developer approves before any implementation.
  2. Build. The orchestrator delegates each section of tasks.md to its owner (infra, backend, frontend), in small slices.
  3. Gate. The package's lint, types and tests run before the section is marked as done.
  4. Review. The reviewer reviews the commits against the standards document and writes review-report.md; blocking findings go back to the dev.
  5. Validation. The validator checks the spec scenarios as a user and writes validation-report.md; failures go back to the dev.
  6. Integration. The orchestrator integrates and the spec-writer archives the change (archived).
Ad-hoc task: a one-off fix, configuration or local refactor does not need a change. The orchestrator delegates straight to the owner of the front with Ad-hoc task: <slug>; the dev follows branch, commit and gate, and if there is a commit the reviewer reviews it. Review and validation come back in the reply, without review-report.md. If it grows, it becomes a change.
Golden rule: the agents do not call each other directly. Every call goes through the orchestrator, which only orchestrates; they communicate through the change files.
