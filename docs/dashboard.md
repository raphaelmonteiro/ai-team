# Dashboard

Reference for the ai-team dashboard: what each part shows, the hooks, the decisions, the notifications and access from outside the machine. For how to open it and the overview, see the "Dashboard" section of the [README](../README.md).

```bash
cd my-project
node .claude/dashboard/server.mjs          # http://127.0.0.1:4321/
# or, from the cloned repo: make dashboard TARGET=~/Sites/project
```

The dashboard reads the transcripts Claude Code writes to `~/.claude/projects/<project>/` (main session and `…/subagents/agent-*.jsonl`) and the project's `openspec/`. It needs no hook and no dependency: Node 18+ and that's it. It updates itself (SSE over `fs.watch`, with fallback polling). Where `fs.watch` has no `recursive` option (Node 18 on Linux), `dashboard/live.mjs` watches each folder of the tree instead (`watchTree`: one non-recursive watcher per folder, rescanned on every event, so a new change or a session's `subagents/` folder joins as soon as it appears; bounded to depth 6 and 2000 watchers). The server computes the state once per change and stores it: with some tab connected (`/events`) and nothing changed since the computation, `GET /api/state` returns the stored state, for any number of tabs; with no tab, each `GET` recomputes. The state is changed by an `fs.watch` event, a `POST /api/answer` or `/api/away`, and the polling tick (5 s), which stays as a safety net: it covers a missed `fs.watch`, transitions that depend only on time (running → no signal after `--stale-min`) and the project's sessions in another folder of `~/.claude/projects`, which `fs.watch` does not observe. The `update` notice is only sent when the state differs from the last one sent, ignoring the `generatedAt` stamp; that is why the header's "updated HH:MM" is the time of the **last change**, not of the last check (with an agent running it changes every tick, because its duration grows). The format of `/api/state` and `/events` did not change.

## Main page

- **Events** (the bottom panel's tab): a rolling log of at least the last 24 h (from when you left, if that is earlier; up to 200 items, the newest kept), with a **since you left** marker at the later of your last real prompt in a team session (`leftAt` in `/api/state`) and **mark as seen** (kept in this browser, per project): what came before it is dimmed, what came after counts as new (the tab's badge). It used to start at your last prompt, so with sessions in use it was nearly always empty. Under the log, a live line per round in progress ("integrator running for 22min · last activity 10s ago", clocks ticking on their own): it is not an event and never counts as new; the round becomes events when it ends. The phone shows the same lines on top of its Events. In order: each round started, finished, failed or interrupted (with the agent, the duration and the error text), test runs red or green with the counts, decisions you answered from the dashboard or the phone (with the answer) and the questions you answered in a team session's terminal (read from the session's transcript, AskUserQuestion's result; one the dashboard already logged is not listed twice), guard refusals, subagent compactions, task marks (who started, paused or finished which tasks, from `task.sh`), a change gone stuck or over budget, the declared stage with its `since` (a time ahead of now, an agent's wrong clock, is left out), and the questions waiting for you now. Built by `dashboard/timeline.mjs` from the state (`timeline` in `/api/state`, up to 200 items, grouped by change, most recent activity first); the answered decisions come from a `Decision` line `ask.mjs` appends to `events.jsonl` (`id`, `kind`, `tool`, `question`, `answer`, `via: dashboard|phone`), which is also the record of who answered what. The strip disappears when there is nothing new.
- **Effort per agent** (in the Team tab, no longer on the Overview): runs, time worked, fresh tokens (hover: cache read and models used), cost, changes touched and the last rounds' duration with its trend; agents that ran but are not in `.claude/agents/` (Explore, general-purpose, plugins) are listed under the table with their runs and cost, followed by the price note and the project total. The team's main session counts as the orchestrator (or the `"agent"` in `settings.json`), with the time of active turns.
- **Team session or ad-hoc session**: with a fixed `"agent"` in `settings.json`, every session belongs to the team. Without it, a session belongs to the team when it called `/team` or `/onboarding` or delegated to an agent in `.claude/agents/`; the others are *ad-hoc sessions* (plain Claude), outside agent effort and changes (the Overview no longer lists them).
- **Change board**: the agents running now (change, stage inferred from the prompt, since when, last activity; "finished" does not prove success); the changes **stuck** (open, nobody running, and the last round `failed` or `interrupted`: the card says which agent, when and why, with the error text the Agent call returned, and offers `/team resume <id>` with a copy button; it leaves the group as soon as a round runs again), in progress, blocked and pending and the 3 latest done (the rest collapsed), with start, `x/y` tasks per section, latest review and validation, rounds, agent switches, time and tokens; and **"waiting for what"** by heuristic (rules in `dashboard/board.mjs`; shows the rule that fired and, with no rule, "undefined"). Clicking a change also lists its `.md` files, served as text at `/changes/<id>/<file>.md` (only proposal, design, tasks, review/validation-report and `specs/**`; traversal refused).
- **Resumed agents**: the coordinator can send a new message to an agent that already returned (the same agent id keeps writing to the same transcript; each resume opens with a user record carrying `origin`, "The coordinator sent a message while you were working: …"). Each leg is its own round (`<agentId>~<n>`, `legRuns` in `collect.mjs`) with its own prompt, description, tokens, tests and time split; a leg ends at its last record, so the time between legs is not counted. Only the last leg can be running: the hooks saw the agent start again after its last stop (or, without hooks, its transcript moved within the activity window).
- **Test runs**: a Bash call of a round whose command is one of the gate's test commands (`BACKEND_CMD_TEST`, `FRONTEND_CMD_TEST`, any `*_CMD_TEST` in `ai-team.conf`) or looks like one (`make test*`, `npm|pnpm|yarn test`, `vitest`, `jest`, `pytest`, `go test`, `mvn … test`, `gradle … test`, `cargo test`, `tests/run.sh` as a command) is read with its output (`dashboard/gate.mjs`): Maven/Surefire totals, Jest, Vitest, pytest, cargo, go test and the ai-team runner give the verdict and the counts; an unrecognised output with a failed exit counts as failed; anything else is ignored. The round keeps the **last run of each suite** (same gate command or same invocation, e.g. `make test-api-unit` run twice) and adds them up (`runs[].tests`: `ok` only when every suite is ok, `passed`, `failed`, `suites`, `summary`, `cmd`, `ts`, `parts` per suite; `testRuns` counts every run) and the change carries the latest round's result (`changes[].tests`, with `agent` and `runId`). The page shows it as a badge on the change card, in the agents tables and as a chip on each round of the conversation; the tooltip has the command and the summary line. Tests passing is the builder's gate, not the validation stage. A red run also keeps **what failed** (`failureDetail` in `gate.mjs`): the failing test names (vitest, jest, pytest, go, cargo, maven, run.sh; up to 10) and an excerpt of the output from the first failure (colors stripped, ~1500 characters). Each round in the conversation has a **what failed** fold (the command, the failing tests, the output), the Problems row opens the same with one click on the row (or **why**; the change name opens the change; it stays open across updates), the badge tooltip lists the first names, and the phone's Inbox shows them too. A stuck change also shows the agent's last words before it stopped. A runner name counts only as a command, not inside a file name (`vitest.config.ts`, `jest.config.js`, `pytest.ini` are not runs).
- **Cost**: every round, change, agent and session carries `usd`, an estimate at the API list price of its model (`dashboard/price.mjs`: input, output, cache read and cache written per million tokens, table dated `pricing.at` in `/api/state`, from Anthropic's pricing page). A project corrects or adds a model in `ai-team.conf` with `PRICE_<MODEL>='<input> <output> <cache read> <cache write>'` (the model id uppercased, dashes as underscores: `PRICE_SONNET_5_5='2 10 0.10 2.50'`); a model with no price counts $0 and is listed in `pricing.unpriced` and in the effort legend; a bare family name (`sonnet`, `opus`, `haiku`, the alias an Agent call may use when nothing recorded which generation ran) is priced as the current generation of the table's date. It is not a bill: plans, batch discounts, a subscription instead of the API and Haiku 5.5 prompts over 100k tokens make the real figure differ. **Budget**: with `BUDGET_SMALL_USD` / `BUDGET_LARGE_USD` in the conf, a change whose size the orchestrator declared (`Size: small|large` in the spec-writer's prompt) gets `budget` (`limit`, `usd`, `over`); over the limit the card turns amber with an "over budget" badge, and the dashboard sends one `budget` notification per change (ntfy event `budget`, on by default; `dashboard/budget.mjs`, record in `.claude/ai-team/budget-notified.json`, so a restart does not repeat it; a change that drops back under, after a raised limit, may notify again).
- **Active agent** on each change in progress, with model, how long it has been working and how many tokens it has cost. Tokens appear in two columns: "new" (input + output + cache written) and "cache read"; `/api/state` also carries the raw fields (`input`, `output`, `cacheRead`, `cacheCreation`) in `usage`/`tokenSplit`.
- **Open the change** (its tab, see Tabs below): the list of rounds, each with start, end, duration, tokens, model, who it came from and who it went to, description; click the row to see the return and the prompt. The change's `.md` files (proposal, tasks, design, reports, specs) open **rendered inside the tab** (`mdToHtml` in `ui.mjs`: headings, lists, code, tables, quotes, links; protocol markers stay visible), with a link per `D-<n>`, `R<k>`, `PV-<n>`, `B<n>`, `L-<n>` and `DT-<n>` that jumps to it and a "raw" link to the plain text. The **diff** view (`GET /changes/<id>/diff`, `dashboard/diff.mjs`) shows what the `change/<id>` branch adds on top of the work branch: per repository that has the branch (the root and a package with its own git, from `BACKEND_DIR`/`FRONTEND_DIR` in the conf), the commits since the merge base with `BACKEND_BRANCH`/`FRONTEND_BRANCH`/`GIT_WORK_BRANCH` (else `HEAD`), each file with added and removed lines, status and the unified diff, collapsible. It reads the repository, not the worktree's uncommitted edits; `git` runs with fixed arguments and no shell; a file is cut at 400 lines and the whole answer at 1.5 MB (`truncated`); a nested repository is never listed as a file of its parent; a change with no branch yet gets a 404 and the tab says so. The page caches the diff for a minute ("refresh" rereads). **Open the agent**: what it does now, then its rounds across all changes.

Definitions: a *round* is one delegation from the orchestrator to an agent (one Agent tool call); *switches* counts how many times the change moved to an agent different from the previous one; a round's change comes from the delegation prompt: the `openspec/changes/<id>` path cited most often (a known id before an unknown one, the first on a tie), else a known id as a bare word when it looks like a slug (a hyphen or 10+ characters; a change called `docs` would match ordinary prose). The stage and the task cited (`task 2.4`, `section 1`) are read from the description first, then from the first 4000 characters of the prompt. A builder round after a review counts as *fix* when it says fix/fixes/fixed, changes requested, blocking or finding(s); paths, backticked text and names like `fix-brand-x` or `pas-fix-its` do not count. Rounds with no change appear under "Outside changes", and ad-hoc task rounds are grouped there by the slug of `Ad-hoc task: <slug>`. A change the rounds cite whose folder is gone from `openspec/changes/` (deleted, not archived) and that no agent is running on gets status `removed` and goes to the collapsed "Removed from openspec/" list (`board.removed`), out of "In progress" and of the /team page stages; it comes back when a round cites it again. Tokens add up `input + output + cache_read + cache_creation` of each response, without counting blocks of the same request twice.

Agent states: running (green), no signal (amber; no activity in the transcript for more than `--stale-min`, default 15, and no end), finished (gray), failed (red), interrupted. Each agent and round shows its originating session (transcript title, else the shortened first prompt, else the short id; a `[Request interrupted by user]` record is not a prompt, it is counted in `mainRuns[].interruptions`).

**Linking a round to its transcript.** Claude Code 2.1.3xx writes `agent-<id>.meta.json` next to each subagent transcript (`agentType`, `description`, `toolUseId`, `model`, `finished`, `stoppedByUser`). The dashboard links a call to its transcript by that `toolUseId` first, then by the result's `agentId`, then by an identical prompt, then by order. A transcript without a visible call (session compacted) takes its agent type, description and model from the meta (the model seen in the transcript wins over the meta one); `finished` ends the round at the transcript's last record, `stoppedByUser` marks it interrupted. The result's `resolvedModel` fills the model when there is no transcript. A change's status is *done* with every task `[x]`, a review APPROVED and no validation saying REJECTED; a declared `approval` stage with nobody running is *pending* (waiting for the developer). A finished reviewer, validator or spec-writer round counts as evidence of its stage in the trail even without a report; Build only by the tasks, Integration only by the archive. A stage before the current one with no evidence at all is *skipped* (`state: "skipped"` in the trail) and the page does not draw it: typically Validation on a backend-only change, which the orchestrator does not send to the validator when "3. Validation" has no tasks; Fix never needed stays pending, and with a declared stage every earlier one is trusted as done.

A change folder is read again only when the folder, `tasks.md`, the two reports or `specs/` changed (mtime and size, cached with the transcripts); a file deeper in `specs/**` is picked up with the next change above it.

### Declared state

An agent running on a **later** stage than the header declares (build, review, fix or validation) wins over it: the trail shows that stage as current, the earlier ones done, and warns that the header still says the old stage (`source: 'running'`, `staleHeader`, `runningAgent` in the trail); an earlier stage running (a fix while the header says validation) does not move it back. The validator template now writes `validation · waiting: validator` when it starts, so the header stays true. A line in the `tasks.md` header decides the stage, the "waiting for whom" and the "next" (the heuristic stays as a fallback; the dashboard shows "declared" or "inferred" and warns if the line is invalid):

```
<!-- state: <stage> · waiting: <who> · since: <yyyy-mm-ddThh:mmZ> · note: <optional short text> -->
```

`stage`: spec, approval, build, review, fix, validation, integration, archived. `waiting`: developer, orchestrator, spec-writer, provisioner, builder, integrator, reviewer, validator, queue.

Who writes it: the orchestrator has no editing tool, so the agent that edits `tasks.md` at that moment does (orchestrator "Flow rules", "Declared state"): the spec-writer at `approval`, at `archived` and when asked to record a review or validation result; the devs at `build`, `review` and `integration` (`gate-and-commit` skill, "Declared state"); the validator at `integration` when it marks section 3. `/team resume <id>` reads this line first and the markers and reports as a fallback (orchestrator "Resuming a change").

### Step list and session question

No hook: the dashboard reads, from the transcript of each team session, the step list (`update_plan` from the desktop app, or `TodoWrite` from the CLI) and the pending question (the end-of-turn one, `wrap_up`, until the next prompt; or an `AskUserQuestion` still unanswered). Open sessions with a list or question get a card below "Agents now", and the current step appears in the "stage" column of the main session. The main session also gets a change: the one of its latest delegated run (ad-hoc included), with that change's current trail step as its stage (`mainRuns[].change`, `.stage`); the card shows that change as a link that opens its tab. A call that came back with an error (session without the app's tools) is ignored. Logic in `dashboard/plan.mjs`; in `/api/state`, `mainRuns[].plan`, `.ask` and `.recap`. Answering through the dashboard: permissions and `AskUserQuestion` under "Decisions through the dashboard"; the end-of-turn question, only with "Away from the computer" on.

`node .claude/dashboard/collect.mjs` prints the same state in the terminal (`--json` for the full JSON).

### The page itself

**Look and navigation.** A terminal look for a tool devs keep open all day: data, ids, commands and numbers in a monospace face (`--mono`: Geist Mono, JetBrains Mono, SF Mono, the system's), prose in a sans one (`--sans`); headings and borders neutral, color only for a state, always next to a glyph (✓ ✗ ● ○ ⊘). Fonts are local stacks: the dashboard loads nothing from outside, so it works offline. Themes: with nothing chosen the page follows the system (dark: `default`, light: `light`); the command palette sets `default`, `dracula`, `fallout` (a Pip-Boy screen: phosphor green, warnings in amber, failures in red, all text in the mono face, Monofonto first when it is installed, tabs in capitals with wide tracking, headings in a `┌─ TITLE ──┐` frame, the status bar as a row of filled boxes, the selected row as an inverted green bar, and an original little dev in the Pip-Boy's line art (backwards cap, headphones, a coffee mug; drawn by `scripts/fallout-dev.mjs`) walking in place of the live dot, standing dimmed when the live channel drops; with CRT on, also a bloom in the middle of the screen, glowing text and a refresh band rolling down), `hacker` or `light` and turns on optional CRT effects (also in Settings › Appearance and, on a phone, More: scanlines and a soft vignette over the whole page, a glow on the `>_` logos, the live mark, the running dots and the headings, a short power-on flicker on a new decision and a flash when a tab opens; with reduced motion on, nothing moves), kept per browser (`localStorage` `ai-team:theme`, `ai-team:crt`) and applied by a one-line script in each page's `<head>` before the first paint. `prefers-reduced-motion` turns every animation off.

- **Layout** (main page, wider than 760 px), after an IDE: an activity bar on the left (explorer, command palette, decisions waiting with a count, Team, Settings), the **explorer**, the editor area with its tabs (for now only Overview, the page described below) and the **status bar** at the bottom. Explorer width, whether it is shown (`⌘B` / Ctrl+B) and the folded groups are kept per browser (`ai-team:layout`); the handle between explorer and editor drags, or moves with ← → when focused. Under 760 px the phone layout replaces it (below). The tree and the layout logic live in `shell.mjs`.
- **Project line** under the explorer heading: the project folder (`~` for home, the full path in the tooltip, copy button), its branch and, for a linked worktree, `⑂ worktree <name>` with the main checkout in the tooltip. Read by the server from `.git` and `HEAD`, without running git (`gitInfo` in `collect.mjs`, `project.git` in `/api/state`).
- **Explorer**: the changes and agents as a tree (a team session shows as `◇ <session name>`, grey and "quiet" after an hour without activity) grouped by state (Decisions, Stuck, In progress, Blocked, Pending, Done, Ad-hoc, Agents), one line each with its glyph, `x/y` tasks, date or running clock; empty groups are left out except In progress; Done and Ad-hoc start folded. A single click opens a change or an agent as a preview tab, a double click as a kept tab (marked in the tree while open); a decision scrolls to its card. The filter on top (`/`) narrows the tree and the Changes table together, opening folded groups that match; ↑ ↓ move in the tree, ← → fold and unfold a group.
- **Sessions** (`sessionsNow` in `shell.mjs`; it replaces "Agents now"): the open Claude sessions of the team, since the orchestrator runs inside each one, with the subagents they launched. The heading counts the active sessions, the subagents working and the quiet ones; sessions quiet for over an hour fold into one line (still open in a terminal). One line per session: session name with its state (● working, a subagent runs; ● waiting for you, a decision or question of that session; idle; quiet, no activity for over 1 h, dimmed and last), change and stage (the working subagent's change when there is one), started and last activity (the session or any of its subagents), and how many subagents are working. A click expands it: the subagents working now (agent, stage, what, since, last activity, model, tokens, cost, **Output** to follow it in the panel, **Agent** to open its tab), the ones that finished earlier in that session as one line each (3, the rest folded), the session's question if any, and its numbers (id, model, fresh, cache read, cost with the working subagents' share, branch, current step) with **Open change**, **Follow in Output** and **Copy resume** (`claude --resume <id>`). Open lines stay open across updates. A running subagent outside an open team session gets a line of its own. Below, **finished recently** (the last 8 rounds that ended) uses the same layout: agent and status (failed / interrupted in yellow), change, stage, ended, how long it took; a click shows what it did, its session, model, tokens, cost and tests, with Output and Agent.
- **Changes table**: a short line per change (state dot, name with one line only for what needs attention: stuck, waiting, over budget, blocked; stage; tasks; who runs; last activity). A click opens the details under it: progress per `tasks.md` section, the stuck or waiting box, agents (runs, time, fresh, cost) and the numbers (started, rounds and handoffs, time, fresh, cache read, cost and budget, tests with their history, review, validation), with **Open change**, **Board** (the kanban) and **Conversation**. The change's name is a link that opens its tab (on a session line too); a click elsewhere on the row expands it. Open rows stay open across updates; the filter hides a row with its details. With anything in progress or pending, the done changes fold into one line.
- **Ad-hoc in the changes table** (table view): an ad-hoc task with an agent on it sits in "In progress" with an `ad-hoc` badge; the rest go to an **Ad-hoc** table below the changes, same columns (stage = `ad-hoc` / `no change`, tasks `—`, the agents, rounds and last activity under the name), the 5 latest and the rest folded. The card view keeps "Outside changes" as cards. The tables share fixed column widths so they line up.
- **Sparklines** (`sparkSvg`, `barsSvg`, `testDots` in `ui.mjs`), from the timestamp of each request in the transcripts (`activityOf` in `collect.mjs`; a run without a transcript counts whole at its end): next to a change's tests badge, its last 10 rounds with a test run (green passed, red failed); in the Team tab, each agent's duration of its last 12 finished rounds with a trend (↑ slower / → steady / ↓ faster, last third against the first); on the hub cards, cost per day for the last 7 local days, today in blue while the project is active (the hub computes each project's state in the background, one at a time, and keeps it 10 min, so `/api/hub` never waits; until then the card has no bars). In `/api/state`: `activity.days`, `changes[].testHistory`, `agents[].recent`.
- **Tabs**: a change or an agent opens as a tab next to Overview (what used to be the drawer, now the full editor width). An open tab is focused instead of duplicated. A preview tab (italic) is replaced by the next preview; a double click, switching its view or opening one of its files keeps it. Each tab remembers its view (Overview, Conversation, Board, Time, Diff; and whether the conversation is compact), the open file, the agent filter, its scroll and expanded rows; the open tabs are kept per browser and page (`ai-team:tabs:<path>`). Alt+1 is Overview, Alt+2…8 the tabs, Alt+9 the last one, Alt+W or × or a middle click closes, Esc goes back to Overview (⌘1…9 and ⌘W belong to the browser). An **agent tab** starts with what the agent is doing now in each change it runs in (task, time, model, tokens, tools, its latest text), then its runs, newest first; the tool-by-tool steps are in the Output panel, which follows the agent's round while its tab is open.
- **Conversation** (a change tab's sub-tab): the change's rounds as a conversation grouped by stage (who called, before and after, the agent's text, the prompt, model, time, tokens, tools, tests, what failed). (The old Compact table of rounds is gone; an unknown sub-tab lands here, and an agent tab still lists its rounds as a table.)
- **Change Overview** (the change tab's first and default sub-tab; tabs saved with another view keep it): **Now** (who runs, or why it is stuck), **Stages** (the full trail; clicking an avatar filters the conversation to that agent; a stage with an agent running on it says **● running** even when the `tasks.md` header still declares an earlier stage, e.g. a validator called while the header says review), a compact **Tasks** list in `tasks.md` order (state glyph, kind badge, who is on it or its measured time, "open the board"), and, on the right, **Properties** (stage, declared or inferred; waiting for; started; last activity; rounds and handoffs; time; fresh and cache read tokens; cost and budget; tests; size) and **Artifacts** (the change's files in reading order: proposal, design, tasks, review and validation reports, specs; a click opens one rendered in the tab). The other sub-tabs (Conversation, Board, Time, Diff) start with the files and the stages on one line (`✓ Spec ×4 — ● Review ×7 — ○ Fix…`); the full trail lives in the Overview only.
- **Board** (a change tab's sub-tab, `Board x/y`; hidden when tasks.md has no tasks): the change's tasks as one kanban. **To do**: not ticked and no running round cites it (⊘ when tasks.md marks it blocked or a dependency is not done, with what it waits for). **Doing**: a running round cites it, ticked or not (a review or a validation of a ticked task is work on it), with the agent, what it does and its clock, and `✓ ticked` when it is; or an open task mark. A running round that marks its tasks (any mark since it started) puts in Doing only the task it marked open: given "Tasks 2.1–2.9", the ones it marked done are Done (when ticked), the one it is on is Doing, and the cited ones it has not started stay in To do as "◷ next in <agent>'s round". **Test**: the last round on it ended but it is not ticked yet, or that round's tests came back red (red border). **Done**: ticked in tasks.md and nobody on it. A round cites every task in its description and the start of its prompt: `task 2.3`, `tasks 2.1–2.7` (each task of the range, in tasks.md order), `tasks 1.1, 1.2 and 1.4`, and, for ids tasks.md knows, a verb before the id (`implement 2.8`) or ids in parentheses (`Validate … round 4 (2.9)`, `(2.8, 2.9)`) (`citedTasks` in `board.mjs`, `taskIds` on each run; `taskList` on each change in `/api/state`). Each card has a badge with the task's kind, from its tasks.md section (back, front, infra, invest, test, docs, review; another section shows its first word), each kind with its own color, apart from the state colors. Clicking a card lists the rounds that cited it. A running round that cites no task of tasks.md (as most review and fix rounds did) is listed above the board under **Now on this change**, so an agent working on the change is never invisible. The agent templates now ask the orchestrator to cite the task ids in every delegation (`Review round 2 — tasks 2.1–2.7`, `Fix tasks 2.3, 2.5 — R10–R14`) and the reviewer to write the task of each finding (`· task <id>`). The rules live in `taskBoard` (`shell.mjs`).
- **Output** (bottom panel, and a change's Output segment on the phone): the latest steps of one round, read from the end of its transcript by `/api/tail?run=<id>&after=<offset>` (`tail.mjs`). No tokens: it only reads the local `.jsonl` Claude Code already writes. Each step: the agent's text, a tool call (its one telling argument: the command, the file, the pattern) and its result (the last 40 lines, folded; a red ✗ when it failed), the round's prompt, a "context compacted" note. A step shows up when Claude Code writes it (after a message or a tool call ends, not word by word); a call still waiting for its result says "running for …". "auto" follows the open change's running round (else its latest), the open agent tab's round, else the first running agent; the list picks any running or recent round. A fold you open or close stays that way while new steps arrive. The page polls every 1.5 s only while the tab is visible, and each poll reads only what the file gained. The server finds the file by the run id (a map kept out of the JSON state), never from a path in the request; the project folder reads as `.` and the home folder as `~`.
- **Review findings** (`parseFindings` in `board.mjs`, `findings` on each change): each `R<k>` of `review-report.md` with its file and line, category, severity, owner, problem and `Fix:`. Its task: the `· task <id>` the reviewer writes (the template asks for it), else the task whose own `<!-- commits: … -->` marker (right under the task line) lists the finding's commit (marked "from the commit"); a commit only in a section-wide marker gives no task. Its status: fixed (an `<!-- applied: R<k> … -->` marker in tasks.md or the report), verified (a later "verification of R<k>" round came back APPROVED), backlog (its severity), else open; an archived change has none open. A task card on the Board and in the Overview list shows its open findings (blocking in red), its round list starts with all its findings; the Overview shows the count in Properties and the findings without a task in a fold; open blocking findings of live changes go to Problems.
- **Time** (a change tab's sub-tab): the change's agent time by stage (spec, development, review, fixes, validation, integration) as a bar and a table, and what the minutes went to inside each stage: **tests** (a gate test command), **lint · types · build** (the gate's other steps), other shell, editing, reading, other tools, and the **model** (the rest of the round: thinking and writing). Each kind is measured from the tool call to its result in the subagent's transcript (`timeSplit` on each run, `roundTime` / `timeBoard` in `shell.mjs`); parallel calls can overlap. **By task**: the rounds that cite only that task are its own time; a round that cites several tasks (`tasks 2.1–2.7`) is shown whole as shared, with no invented split. A task card shows `⏱ own + shared`, and its round list shows each round's duration and split.
- **Task marks** (`dashboard/task.sh`): every agent that works on a task of `tasks.md` (devs, reviewer, validator, spec-writer, the orchestrator when it integrates) runs `.claude/dashboard/task.sh start|pause|done <change-id> <task-id>[,<task-id>…] <agent>` from the project root; the agent templates say when. The script writes one `Task` line to `.claude/ai-team/events.jsonl` (local, never in git), is plain bash (any agent of any AI tool can call it) and never fails the caller (a wrong call prints the usage and exits 0). The collector hands each change its marks (`taskMarks`); `markIntervals` in `shell.mjs` turns them into intervals: `start` opens the listed tasks for that agent and closes the ones it had open and did not list (it moved on), `pause`/`done` close them, a task still open closes at the end of the agent's round (or counts to now while the round runs), and an interval never outlives the round it started in. With marks, a task's **measured** time replaces own/shared on its card and in Time › By task (by stage in the tooltip), an open mark puts the task in Doing, and marked work on an unticked task puts it in Test. Rounds from before the marks keep the own/shared view.
- **Team and Settings tabs** (activity bar, palette, `#team` / `#settings`). **Team**: the agents as a table (running now, what each owns from its description, model, tools, runs, time and cost from the state, a link to its `.md` and to its agent tab), how to call the team, the gates one step per line with a repeated `PATH=` prefix shown once (and a button to copy the full command), the project context from `ai-team.conf`. **Settings**, in the VS Code style: a search box, the **User** scope (`notify.json` through `/api/notify`, saved on change, text fields on blur or Enter; the theme, CRT and a layout reset, kept in the browser) and **This project** (the per-project events, also saved; and `ai-team.conf`: see "Editing ai-team.conf" below). The ntfy warning sits on top with a one-click fix; "Open notify.json" shows the raw values (never the token). HTML built in `views.mjs`. The old `/team` and `/notifications` pages still answer.
- **Editing `ai-team.conf`** (Settings › This project; `conf-edit.mjs`, `/api/conf*`). The safe keys are fields: project name and description, output language, hub team, test personas, the branches, the docs paths and the change budgets. A change marks its row; the bar over the fields says how many and offers **Review**, which runs the clone's `install.sh --render --dry-run --set …` and lists the change (old → new), the files that would be rewritten (agents, `project-context.md`), the generated files edited by hand that the render keeps as they are, and the agents running now (they read their files when a round starts, so it applies from their next round). **Save and re-render** copies the conf to `.claude/ai-team/conf-history/` (the last 10, out of git) and runs the same command for real; **Undo last change** puts the newest copy back and renders again. Each value is checked twice (page and server): one line, no single quote, branch names, paths inside the project, amounts. The gate commands (`*_CMD_*`) are run by the agents and never change from a browser (Team tab lists them; change one from the clone with `--set`); the detected keys and the conf version are not shown. It only writes where the clone is next to the dashboard (the hub, or a server started from the clone): an installed copy has no `install.sh` and shows the keys read-only with the `--set` command to copy. The installer runs without a shell (an argument list) and in the background, one save per project at a time; writing needs the login when the request comes from outside, same origin, JSON.
- **Panel** under the editor (Ctrl+`, the Panel button in the status bar or the palette show or hide it; height, visibility and tab kept per browser; the handle above it drags or moves with ↑ ↓). **Problems**: the decision cards first (same forms, Enter, A/D, typed text kept), then stuck changes with their `/team resume` to copy, red tests, blocked tasks and agents without a signal; a row opens its change or agent tab. A new decision opens the panel on Problems; links to the decisions (status bar, agents table) open it too. **Events**: the since-you-left timeline as one log, oldest first and newest at the bottom (it stays pinned to the bottom unless you scroll up), with a marker where the unseen part starts and "mark as seen"; already seen rows stay, dimmed. **Output**: reserved for the live output of an agent, which needs a server route. The tab counts: problems (red if something failed), new events.
- **Phone** (under 760 px; `mobile.mjs`): a layout of its own instead of the IDE shell, for deciding and checking rather than analysing. A top bar (project, connection, running count, branch, estimated cost) and a bottom bar with **Home** (the decisions first, answered in place: the decision forms, the same element as the desktop's, are moved in; then stuck changes; the active **Sessions** as rows that open a session screen, quiet ones folded; the open changes with stage, agent, last activity and tasks progress, pending in yellow; done and ad-hoc in one line), **Inbox** (the same decision forms when Home is not shown; then stuck, failing and blocked changes with the resume command to copy; its badge counts them), **Events** (the since-you-left log, newest first) and **More** (away switch, **Notifications**, the installed team, the theme). A session opens full screen: its state and question, change, stage, started and last activity, the subagents working now (Output opens the change's live tail), the ones that finished earlier, its numbers and the resume command to copy. **More › Notifications** is the phone's Settings › User: away, ntfy topic (or a new random one), server, token, dashboard address, the events, "only when away", the content switch with the public-topic warning and a test button, saved on change. A change opens full screen with a back arrow (the phone's back button works too): its stage bar, who runs now (or why it is stuck), and Tasks (one kanban column at a time behind chips, Doing first) / Output / Events / Info (progress per section, the waiting box, rounds, time, cost, tests with their history, review, validation, agents). No diff, rounds or files on the phone. `#inbox` opens the Inbox on a phone and the Problems panel on a wide screen; a decision notification links there.

## Hooks

The `settings.json` created by the installer points `SubagentStart`/`SubagentStop` (dashboard) and `SessionStart`/`UserPromptExpansion` (`/team`) to `.claude/dashboard/hook.sh` (quoted in the command, so a project path with a space works), which forwards to `hook.mjs` (Node 18+) and writes `.claude/ai-team/events.jsonl` (outside git: see "What to version" in the README); with `--no-dashboard` only `hook.sh` and `hook.mjs` are copied. `events.jsonl` does not grow without limit: once it exceeds `AI_TEAM_EVENTS_MAX_BYTES` (default 1048576, 1 MiB; an invalid value means the default) the hook renames it to `events.jsonl.1` (replacing the previous generation) and starts a new file with the `TeamStart` events of each session (up to half the limit, the most recent); only one hook rotates at a time (lock `events.jsonl.lock`, created with `wx`) and no line is lost. A lock older than 30 s is considered abandoned (a hook that died) and taken over; accepted risk: two hooks taking over the same abandoned lock at the same instant may both rotate, and the second `rename` replaces the just-created `.1` generation (the damage is the one described below: exact start and end of old rounds fall back to the transcript). The dashboard and the post-compaction reminder read both generations; what is lost is the exact start and end of rounds older than two generations, which fall back to transcript timestamps. An old dashboard with a new hook reads only the current file (same loss, until the dashboard restarts). The `TeamStart` event (from `/team`, `/onboarding` or `claude --agent orchestrator`) tells the dashboard exactly which sessions belong to the team. With these events, the start and end of each round are exact even for background agents; without them, the dashboard uses transcript timestamps and considers a round with no recorded end active if it had activity within `--stale-min` (default 15 min). An Agent call that comes back with an error (`is_error`, message as text) ends there with status failed. If `settings.json` already existed, the installer adds only the missing ai-team hooks (see "Decisions through the dashboard").

**Finding node.** The desktop app runs the hooks with a short PATH (no nvm, often no Homebrew). `hook.sh` uses `AI_TEAM_NODE` when set (that binary only), else `node` on PATH, else the usual places: `~/.nvm/versions/node/*/bin`, `~/.volta/bin`, fnm's default alias, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`. With no node anywhere it exits 0 and writes `.claude/ai-team/hook-no-node` (`since`, `path`), which the dashboard shows as a warning at the top (`hooks.noNode` in `/api/state`): no events, no reminder after compaction, no notifications. The next hook that finds node removes the file. The `PermissionRequest` hook calls `node` directly (see below): without node on PATH, Claude Code reports that hook's failure itself.

**Compaction of a subagent.** Subagents compact on their own when their context fills (Claude Code writes a `compact_boundary` record in their transcript). Each team agent carries in its frontmatter a `PreCompact` hook (`hooks:` in `.claude/agents/<role>.md`, rendered from the template; it runs only while that agent is active) that calls `hook.sh compact <role>`: `hook.mjs` prints the instructions for the compaction summary (Claude Code caps them at 10 000 characters), which make the summary open with an "ai-team context" block: role and agent file to reread, change or ad-hoc slug, `tasks.md` section and markers, worktree and branch, commits and gate, open `PV-<n>`/`R<k>`/`B<n>`, the exact next step and what must not be redone. Each agent's "After compaction" section says what to reread and to continue from that step. The compaction is logged as a `Compact` event (`agent_type`, `trigger`) in `events.jsonl`. The orchestrator keeps the existing `/team` reminder (`SessionStart` with `source: compact`). Not covered by the docs, so not relied on: whether `SessionStart` fires inside a subagent and whether the agent's prompt is re-applied after its compaction.

**Agent guard.** The same `hook.sh` runs on `PreToolUse` (matcher `Bash|Edit|Write|MultiEdit|NotebookEdit`) and, inside a team subagent (`agent_type` in the hook input), `guard.mjs` refuses what the role's agent file forbids: for builder, integrator and provisioner `git add -A|--all|-u|.`, `--no-verify`, `git stash|restore|clean`, `reset --hard`, `checkout -- <path>` and a forced push; for the spec-writer the `add`/`--no-verify` part; for reviewer and validator any git subcommand that changes a repository or working tree (`show`, `log`, `diff`, `status`, `cat-file`, `branch` listings, `stash list` and `worktree list` go on) and any Write/Edit outside their own files in `openspec/changes/<id>/` (reviewer: `review-report.md`; validator: `validation-report.md` and `tasks.md`, where it marks section 3 and the state line); for every role `compose down -v|--volumes`, `docker volume rm|prune` and `find /`. The command is judged piece by piece (`&&`, `||`, `;`, `|`, newlines), so `cd x && git add -A` is refused and `git log | head` is not. The refusal goes back to the agent as `permissionDecision: deny` with the reason and the agent file to reread, and is logged as a `Guard` event in `events.jsonl`. The user's session, the `/team` orchestrator, the built-in agents and any agent outside the six roles are never judged; `AI_TEAM_GUARD=0` turns it off. It is a safety net, not a security boundary: a command wrapped in `sh -c` or a script gets past it, as it would past the prose. It is installed whenever `hook.sh` is (also with `--no-dashboard`), and `node .claude/dashboard/settings.mjs` adds it to an older `settings.json`. The reviewer has `Edit` because of it: it appends a round to `review-report.md` instead of rewriting the file and checking a `shasum`.

## Decisions through the dashboard

The `PermissionRequest` hook (`node .claude/dashboard/ask.mjs`, which the installer puts in a new `settings.json`) writes each permission request and each `AskUserQuestion` to `.claude/ai-team/pending/` and waits for the answer. The dashboard shows "Decisions waiting for you" at the top of the Overview (a question is not a problem: the Problems panel no longer holds it nor opens for it; the explorer's Decisions group, the activity bar badge and the status bar still flag it): the command (or file) with **Allow once** / **Deny** (with a reason, which goes back to Claude), and the questions with their options, multi-select and free-text "Other". The app shows its own dialog at the same time and the first answer wins; once answered in the app (the transcript gets the `tool_result`), the pending item disappears. With no answer, the hook gives up after `AI_TEAM_ASK_WAIT_S` (default 280 s); with **away from the computer** on, it waits `AI_TEAM_AWAY_WAIT_S` (default 86100 s, ~24 h). The hook `timeout` is 86400; a project installed with a lower one (300, 3600) is adjusted by `node .claude/dashboard/settings.mjs`. Once the hook gives up on a main-session call, the app's dialog is still open, so the item stays in "Decisions waiting for you" read-only (dashed card, "answer in the terminal"; `expired` in `pending`, without the pid or the secret, and `POST /api/answer` refuses it with 409) until the transcript gets its `tool_result`, the session closes or a week passes; a subagent's call is denied when the hook leaves, so it goes. The question also appears on the session card, read-only: while the hook waits, the card points to "Decisions waiting for you"; afterwards, it says the dashboard is no longer waiting and the answer goes in the session. A background subagent has no dialog: the dashboard is the only place to approve. `AI_TEAM_ASK=0` disables it. Routes: `pending` in `/api/state` and `POST /api/answer` (`{ id, behavior: allow|deny, message?, answers? }`, JSON only and same origin). Since the dashboard approves commands, access from outside the machine requires a token (see "Access from outside the machine"). Project with an existing `settings.json`: the installer adds only the missing ai-team hooks (`dashboard/settings.mjs`, with a copy in `settings.json.bak-ai-team`; the rest of the file stays the same). To do this without reinstalling: `node .claude/dashboard/settings.mjs` (`--dry-run` shows it first). If the JSON has comments, it does not write and shows the snippet; the `PermissionRequest` one is

```json
"PermissionRequest": [{ "hooks": [{ "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR/.claude/dashboard/ask.mjs\"", "timeout": 86400 }] }]
```

## Away from the computer

The app's end-of-turn question (the box with buttons) is neither a permission nor an `AskUserQuestion`: answering it means sending a message to the session, which no hook does after the turn has ended. That is why the dashboard only shows it ("answer in the session") and the phone gets "question for you" with the question and the options. To answer through the dashboard, turn on **away from the computer** in the header (`.claude/ai-team/away.json`, per project): when the turn is about to end with a question, the `Stop` hook (`timeout` 86400) holds the end of the turn and waits up to `AI_TEAM_AWAY_WAIT_S` (default 86100 s, ~24 h); the dashboard shows the options, a text field and **Leave it to the app**, and the answer comes back as `{"decision":"block","reason":…}`, which Claude treats as your answer (the app records it as "Stop hook feedback"). While it waits, the app shows the session running, without its buttons; with no answer, or with the mode turned off midway, the turn ends and the question appears in the app. Route: `GET/POST /api/away`.

**Proposal approval.** The orchestrator asks it with `AskUserQuestion` (`Approve` / `Changes`, the text of the changes through "Other"), so it is a pending item like any other: the dashboard and the phone catch it without away mode, in the desktop app and in a terminal session alike. The wait is the usual 280 s (`AI_TEAM_ASK_WAIT_S`); for longer, turn on away mode.

## Phone notifications (ntfy)

With `~/.config/ai-team/notify.json`, the hooks notify through the [ntfy](https://ntfy.sh) app: new decision (permission or question, the same as in the dashboard), agent finished (`SubagentStop`, with the start of its summary), session that ended its turn and waits for you (`Stop`), turn stopped by an error (`StopFailure`: usage limit, overloaded API, login failure…) and session closed (`SessionEnd`: `/clear`, `/resume`, logout, exit; the hook has `timeout` 10 because Claude Code's default is 1.5 s). Interrupting with Esc or the stop button sends nothing: Claude Code has no hook for that (`Stop` does not run in that case). Old configs get the new events turned on (`eventsVersion`). Without the file, nothing is sent. To start:

```bash
node .claude/dashboard/notify.mjs setup      # creates the file with a random topic and explains how to subscribe on the phone
node .claude/dashboard/notify.mjs test       # sends a test notification
```

**Buttons.** With `dashboardUrl` set (Settings tab; the address the phone reaches, e.g. the Tailscale one, or the project page `.../p/<name>/` in a hub), a decision notification carries [ntfy action buttons](https://docs.ntfy.sh/publish/#action-buttons): **Allow** / **Deny** for a permission, one per option for a single question with exactly two options (the proposal approval, a yes/no end-of-turn question in away mode), and always **Open**, which opens the dashboard on `#inbox` (the Inbox on a phone, the Problems panel on a wide screen; tapping the notification itself goes there too). Anything else (three or more options, multi-select, several questions, free text) gets only **Open**: the dashboard is the better place for it. The answer buttons `POST <dashboardUrl>/api/answer` with the item's one-time `secret` (written by `ask.mjs` in the pending file, never listed by `/api/state`): that route is reachable from outside without login, but only answers the item whose secret it carries, once (`already answered` afterwards); the dashboard token never travels through ntfy. With `detail: false` the body would carry the question text, so only **Open** goes. On a public ntfy.sh topic without a token, whoever guesses the topic could tap the buttons: use a token or your own server before turning the buttons on (same advice as for the message content).

The installer handles this: if the PC has no config yet, it asks for the topic (enter skips, `new` generates one) and offers to send a test; without a terminal, use `install.sh --ntfy-topic <topic>` (on a PC already configured, it only changes the topic). It can also be configured from the dashboard's **Settings** tab (on a phone, More › Notifications; the old `/notifications` page redirects there): topic, server, token (never shown back), events, content, dashboard address, events from that project only (or a muted project) and a test button. The config belongs to the PC (applies to all projects); the hooks that fire live in each project's `settings.json`. In the file: `ntfy.server`/`topic`/`token` (own server or ntfy.sh with a token), `on` (`decision`, `agent_stop`, `turn_stop`), `detail` (`false` sends only the title, with no command or agent text; public ntfy.sh is open to anyone who knows the topic) and `dashboardUrl` (opened when the notification is tapped). `AI_TEAM_NOTIFY=0` disables it. Sending runs in the background and never holds the hook. Whatever `detail` says, bearer tokens, `key=value` secrets (token, password, api key…), `--token x` arguments, credentials in URLs and known key shapes (AWS, GitHub, Slack, OpenAI-style) are blanked before anything leaves the machine (`redact` in `notify.mjs`). A new config made by `setup` starts with `detail: false` (public ntfy.sh with no token: anyone who guesses the topic reads it; the Notifications page warns when the content is on in that situation) and `quietAtComputer: true`: "agent finished" and "session waiting for you" only go out with the dashboard's "away from the computer" mode on in that project; decisions, errors and session end always go. An existing config keeps its behaviour until changed on the page. When the away-mode wait runs out, the phone gets "the dashboard is no longer waiting" and the question is in the app; the turn that goes on after an answer does not ask the same question again. On the Notifications page reached from outside (Tailscale, a tunnel), the dashboard address is suggested from the one in use. A new `settings.json` comes with the `Stop`, `StopFailure` and `SessionEnd` hooks; in an existing one, the installer adds the missing ones.

## Access from outside the machine

The dashboard stays on `127.0.0.1`, open to whoever is on the machine. A request that arrives through a proxy (`X-Forwarded-For`), with another `Host` or from another interface only gets in with the token: a cookie after `/login` (30 days, `HttpOnly`, `SameSite=Strict`, `Secure` behind HTTPS) or `Authorization: Bearer`. Without a token, outside access is refused. The token lives in `~/.config/ai-team/token` (or `AI_TEAM_TOKEN`); create it with `node .claude/dashboard/auth.mjs token` and restart the dashboard. To open it on the phone, the recommended path is **Tailscale Serve** (HTTPS only inside your tailnet, no open port):

```bash
node .claude/dashboard/auth.mjs token          # once per machine
node .claude/dashboard/server.mjs              # or --hub
tailscale serve --bg 4321                      # https://<machine>.<tailnet>.ts.net/ → 127.0.0.1:4321
```

On the phone, with the Tailscale app on, open the `ts.net` address, paste the token and you're done. Put that address in `dashboardUrl` in `notify.json` so the notification opens the dashboard (the Notifications page suggests it when opened from there). Do not use `tailscale funnel` (public on the internet). Alternative with your own domain: Cloudflare Tunnel + Cloudflare Access.

## Running it

`node .claude/dashboard/server.mjs --help` prints the flags; `--version` the copy's version (also at startup and in `GET /api/health`, which answers `{ ok, version, mode, projectDir | hubFile, uptimeS, pid }` without reading any transcript: the probe for a supervisor). An unknown flag stops the server with the usage, instead of starting it on the wrong project. `--port 0` takes a free port and prints the one bound. `AI_TEAM_LOG=silent` prints nothing, `debug` logs every request.

**As a service (macOS, launchd)**, so the phone flow does not depend on a terminal staying open: `~/Library/LaunchAgents/eu.ai-team.dashboard.plist` with `ProgramArguments` = `[/path/to/node, /path/to/project/.claude/dashboard/server.mjs]` (or `--hub`), `RunAtLoad` and `KeepAlive` true, `StandardOutPath`/`StandardErrorPath` to a log file, then `launchctl load ~/Library/LaunchAgents/eu.ai-team.dashboard.plist`. On Linux, a user `systemd` unit with `ExecStart=/usr/bin/node .../server.mjs`, `Restart=on-failure` and `WantedBy=default.target` (`systemctl --user enable --now ai-team-dashboard`). Give the service the same `HOME` as the user so it finds `~/.claude` and `~/.config/ai-team`.

**Updating an installed copy.** `.claude/dashboard/` is code, never edited by hand, so a new `install.sh` run (from the clone: `./install.sh .` or `make install TARGET=…`) replaces the files that changed without `--force` ("updated" in the log) and removes the files earlier versions left there that no source has any more (`team.html`, `equipe.html`, `notificacoes.html`, `cycle-default.html`, `cycle.html`; `--check` lists them). `--force` is still what overwrites hand-edited generated Markdown. Compare `node .claude/dashboard/server.mjs --version` with the clone's `dashboard/version.mjs` to know whether a project is behind. The installer also adds `.claude/ai-team/` to the project's `.gitignore` when it is a git repository (hook log, pending decisions and answers, which carry tool inputs).

## Team page

The team lives in the main page's **Team tab** (above; `/team` redirects to `./#team`, and on a phone `#team` opens More). Not to be confused with the `/team` skill, which calls the team into a session. Data: `/api/team` (JSON `{project, agents, context, entry, hasConf}`, read-only; agents from `<project>/.claude/agents/*.md` frontmatter `name`, `description`, `model`, `tools`; `entry` carries only `fixedAgent` and skill and hook booleans), `/agents/<name>.md` (only `[a-z0-9-]+`). Without `ai-team.conf` or without agents, the tab opens anyway (uses the folder name and says there are no agents).

Exposed conf keys (closed list in `dashboard/team.mjs`; `GIT_REMOTE`, `TEST_PERSONAS` and the rest are not exposed): `PROJECT_NAME`, `PROJECT_DESCRIPTION`, `LAYOUT`, `HAS_OPENSPEC`, `CI`, `HUB_TEAM`, `GIT_DEFAULT_BRANCH`, `GIT_WORK_BRANCH`, `GIT_PROTECTED_BRANCHES`, `BACKEND_`/`FRONTEND_` + `DIR`, `STACK`, `BRANCH`, `PROTECTED_BRANCH`, plus `BACKEND_GATE`/`FRONTEND_GATE` (the `*_CMD_LINT/FORMAT/TYPECHECK/TEST/BUILD` joined by `; `, as the installer does) and `DOCS_CONTEXT`, `DOCS_STANDARDS`, `DOCS_ENV`.
