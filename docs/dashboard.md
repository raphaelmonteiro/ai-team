# Dashboard

Reference for the ai-team dashboard: what each part shows, the hooks, the decisions, the notifications and access from outside the machine. For how to open it and the overview, see the "Dashboard" section of the [README](../README.md).

```bash
cd my-project
node .claude/dashboard/server.mjs          # http://127.0.0.1:4321/
# or, from the cloned repo: make dashboard TARGET=~/Sites/project
```

The dashboard reads the transcripts Claude Code writes to `~/.claude/projects/<project>/` (main session and `…/subagents/agent-*.jsonl`) and the project's `openspec/`. It needs no hook and no dependency: Node 18+ and that's it. It updates itself (SSE over `fs.watch`, with fallback polling). Where `fs.watch` has no `recursive` option (Node 18 on Linux), `dashboard/live.mjs` watches each folder of the tree instead (`watchTree`: one non-recursive watcher per folder, rescanned on every event, so a new change or a session's `subagents/` folder joins as soon as it appears; bounded to depth 6 and 2000 watchers). The server computes the state once per change and stores it: with some tab connected (`/events`) and nothing changed since the computation, `GET /api/state` returns the stored state, for any number of tabs; with no tab, each `GET` recomputes. The state is changed by an `fs.watch` event, a `POST /api/answer` or `/api/away`, and the polling tick (5 s), which stays as a safety net: it covers a missed `fs.watch`, transitions that depend only on time (running → no signal after `--stale-min`) and the project's sessions in another folder of `~/.claude/projects`, which `fs.watch` does not observe. The `update` notice is only sent when the state differs from the last one sent, ignoring the `generatedAt` stamp; that is why the header's "updated HH:MM" is the time of the **last change**, not of the last check (with an agent running it changes every tick, because its duration grows). The format of `/api/state` and `/events` did not change.

## Main page

- **Since you left**: the Events tab of the bottom panel, with what happened after the later of your last real prompt in the team session (`leftAt` in `/api/state`, else the last 24 h) and **mark as seen** (kept in this browser's `localStorage`, per project): per change, in order, each round started, finished, failed or interrupted (with the agent, the duration and the error text), test runs red or green with the counts, decisions you answered from the dashboard or the phone (with the answer), guard refusals, subagent compactions, a change gone stuck or over budget, the declared stage with its `since`, and the questions waiting for you now. Built by `dashboard/timeline.mjs` from the state (`timeline` in `/api/state`, up to 200 items, grouped by change, most recent activity first); the answered decisions come from a `Decision` line `ask.mjs` appends to `events.jsonl` (`id`, `kind`, `tool`, `question`, `answer`, `via: dashboard|phone`), which is also the record of who answered what. The strip disappears when there is nothing new.
- **Effort per agent**: time worked, tokens (input, output, cache read and written), rounds, changes touched, models used. The team's main session counts as the orchestrator (or the `"agent"` in `settings.json`), with the time of active turns.
- **Team session or ad-hoc session**: with a fixed `"agent"` in `settings.json`, every session belongs to the team. Without it, a session belongs to the team when it called `/team` or `/onboarding` or delegated to an agent in `.claude/agents/`; the others are *ad-hoc sessions* (plain Claude), shown separately with count, time and tokens, outside agent effort and changes.
- **Change board**: the agents running now (change, stage inferred from the prompt, since when, last activity; "finished" does not prove success); the changes **stuck** (open, nobody running, and the last round `failed` or `interrupted`: the card says which agent, when and why, with the error text the Agent call returned, and offers `/team resume <id>` with a copy button; it leaves the group as soon as a round runs again), in progress, blocked and pending and the 3 latest done (the rest collapsed), with start, `x/y` tasks per section, latest review and validation, rounds, agent switches, time and tokens; and **"waiting for what"** by heuristic (rules in `dashboard/board.mjs`; shows the rule that fired and, with no rule, "undefined"). Clicking a change also lists its `.md` files, served as text at `/changes/<id>/<file>.md` (only proposal, design, tasks, review/validation-report and `specs/**`; traversal refused).
- **Test runs**: a Bash call of a round whose command is one of the gate's test commands (`BACKEND_CMD_TEST`, `FRONTEND_CMD_TEST`, any `*_CMD_TEST` in `ai-team.conf`) or looks like one (`make test*`, `npm|pnpm|yarn test`, `vitest`, `jest`, `pytest`, `go test`, `mvn … test`, `gradle … test`, `cargo test`, `tests/run.sh` as a command) is read with its output (`dashboard/gate.mjs`): Maven/Surefire totals, Jest, Vitest, pytest, cargo, go test and the ai-team runner give the verdict and the counts; an unrecognised output with a failed exit counts as failed; anything else is ignored. The round keeps the **last run of each suite** (same gate command or same invocation, e.g. `make test-api-unit` run twice) and adds them up (`runs[].tests`: `ok` only when every suite is ok, `passed`, `failed`, `suites`, `summary`, `cmd`, `ts`, `parts` per suite; `testRuns` counts every run) and the change carries the latest round's result (`changes[].tests`, with `agent` and `runId`). The page shows it as a badge on the change card, in the agents tables and as a chip on each round of the conversation; the tooltip has the command and the summary line. Tests passing is the builder's gate, not the validation stage.
- **Cost**: every round, change, agent and session carries `usd`, an estimate at the API list price of its model (`dashboard/price.mjs`: input, output, cache read and cache written per million tokens, table dated `pricing.at` in `/api/state`, from Anthropic's pricing page). A project corrects or adds a model in `ai-team.conf` with `PRICE_<MODEL>='<input> <output> <cache read> <cache write>'` (the model id uppercased, dashes as underscores: `PRICE_SONNET_5_5='2 10 0.10 2.50'`); a model with no price counts $0 and is listed in `pricing.unpriced` and in the effort legend; a bare family name (`sonnet`, `opus`, `haiku`, the alias an Agent call may use when nothing recorded which generation ran) is priced as the current generation of the table's date. It is not a bill: plans, batch discounts, a subscription instead of the API and Haiku 5.5 prompts over 100k tokens make the real figure differ. **Budget**: with `BUDGET_SMALL_USD` / `BUDGET_LARGE_USD` in the conf, a change whose size the orchestrator declared (`Size: small|large` in the spec-writer's prompt) gets `budget` (`limit`, `usd`, `over`); over the limit the card turns amber with an "over budget" badge, and the dashboard sends one `budget` notification per change (ntfy event `budget`, on by default; `dashboard/budget.mjs`, record in `.claude/ai-team/budget-notified.json`, so a restart does not repeat it; a change that drops back under, after a raised limit, may notify again).
- **Active agent** on each change in progress, with model, how long it has been working and how many tokens it has cost. Tokens appear in two columns: "new" (input + output + cache written) and "cache read"; `/api/state` also carries the raw fields (`input`, `output`, `cacheRead`, `cacheCreation`) in `usage`/`tokenSplit`.
- **Click on the change**: the list of rounds, each with start, end, duration, tokens, model, who it came from and who it went to, description; click the row to see the return and the prompt. The change's `.md` files (proposal, tasks, design, reports, specs) open **rendered inside the drawer** (`mdToHtml` in `ui.mjs`: headings, lists, code, tables, quotes, links; protocol markers stay visible), with a link per `D-<n>`, `R<k>`, `PV-<n>`, `B<n>`, `L-<n>` and `DT-<n>` that jumps to it and a "raw" link to the plain text. The **diff** view (`GET /changes/<id>/diff`, `dashboard/diff.mjs`) shows what the `change/<id>` branch adds on top of the work branch: per repository that has the branch (the root and a package with its own git, from `BACKEND_DIR`/`FRONTEND_DIR` in the conf), the commits since the merge base with `BACKEND_BRANCH`/`FRONTEND_BRANCH`/`GIT_WORK_BRANCH` (else `HEAD`), each file with added and removed lines, status and the unified diff, collapsible. It reads the repository, not the worktree's uncommitted edits; `git` runs with fixed arguments and no shell; a file is cut at 400 lines and the whole answer at 1.5 MB (`truncated`); a nested repository is never listed as a file of its parent; a change with no branch yet gets a 404 and the drawer says so. The page caches the diff for a minute ("refresh" rereads). **Click on the agent**: its rounds across all changes.

Definitions: a *round* is one delegation from the orchestrator to an agent (one Agent tool call); *switches* counts how many times the change moved to an agent different from the previous one; a round's change comes from the delegation prompt: the `openspec/changes/<id>` path cited most often (a known id before an unknown one, the first on a tie), else a known id as a bare word when it looks like a slug (a hyphen or 10+ characters; a change called `docs` would match ordinary prose). The stage and the task cited (`task 2.4`, `section 1`) are read from the description first, then from the first 4000 characters of the prompt. A builder round after a review counts as *fix* when it says fix/fixes/fixed, changes requested, blocking or finding(s); paths, backticked text and names like `fix-brand-x` or `pas-fix-its` do not count. Rounds with no change appear under "Outside changes", and ad-hoc task rounds are grouped there by the slug of `Ad-hoc task: <slug>`. A change the rounds cite whose folder is gone from `openspec/changes/` (deleted, not archived) and that no agent is running on gets status `removed` and goes to the collapsed "Removed from openspec/" list (`board.removed`), out of "In progress" and of the /team page stages; it comes back when a round cites it again. Tokens add up `input + output + cache_read + cache_creation` of each response, without counting blocks of the same request twice.

Agent states: running (green), no signal (amber; no activity in the transcript for more than `--stale-min`, default 15, and no end), finished (gray), failed (red), interrupted. Each agent and round shows its originating session (transcript title, else the shortened first prompt, else the short id; a `[Request interrupted by user]` record is not a prompt, it is counted in `mainRuns[].interruptions`).

**Linking a round to its transcript.** Claude Code 2.1.3xx writes `agent-<id>.meta.json` next to each subagent transcript (`agentType`, `description`, `toolUseId`, `model`, `finished`, `stoppedByUser`). The dashboard links a call to its transcript by that `toolUseId` first, then by the result's `agentId`, then by an identical prompt, then by order. A transcript without a visible call (session compacted) takes its agent type, description and model from the meta (the model seen in the transcript wins over the meta one); `finished` ends the round at the transcript's last record, `stoppedByUser` marks it interrupted. The result's `resolvedModel` fills the model when there is no transcript. A change's status is *done* with every task `[x]`, a review APPROVED and no validation saying REJECTED; a declared `approval` stage with nobody running is *pending* (waiting for the developer). A finished reviewer, validator or spec-writer round counts as evidence of its stage in the trail even without a report; Build only by the tasks, Integration only by the archive. A stage before the current one with no evidence at all is *skipped* (`state: "skipped"` in the trail) and the page does not draw it: typically Validation on a backend-only change, which the orchestrator does not send to the validator when "3. Validation" has no tasks; Fix never needed stays pending, and with a declared stage every earlier one is trusted as done.

A change folder is read again only when the folder, `tasks.md`, the two reports or `specs/` changed (mtime and size, cached with the transcripts); a file deeper in `specs/**` is picked up with the next change above it.

### Declared state

A line in the `tasks.md` header decides the stage, the "waiting for whom" and the "next" (the heuristic stays as a fallback; the dashboard shows "declared" or "inferred" and warns if the line is invalid):

```
<!-- state: <stage> · waiting: <who> · since: <yyyy-mm-ddThh:mmZ> · note: <optional short text> -->
```

`stage`: spec, approval, build, review, fix, validation, integration, archived. `waiting`: developer, orchestrator, spec-writer, provisioner, builder, integrator, reviewer, validator, queue.

Who writes it: the orchestrator has no editing tool, so the agent that edits `tasks.md` at that moment does (orchestrator "Flow rules", "Declared state"): the spec-writer at `approval`, at `archived` and when asked to record a review or validation result; the devs at `build`, `review` and `integration` (`gate-and-commit` skill, "Declared state"); the validator at `integration` when it marks section 3. `/team resume <id>` reads this line first and the markers and reports as a fallback (orchestrator "Resuming a change").

### Step list and session question

No hook: the dashboard reads, from the transcript of each team session, the step list (`update_plan` from the desktop app, or `TodoWrite` from the CLI) and the pending question (the end-of-turn one, `wrap_up`, until the next prompt; or an `AskUserQuestion` still unanswered). Open sessions with a list or question get a card below "Agents now", and the current step appears in the "stage" column of the main session. The main session also gets a change: the one of its latest delegated run (ad-hoc included), with that change's current trail step as its stage (`mainRuns[].change`, `.stage`); the card shows that change as a link that opens its drawer. A call that came back with an error (session without the app's tools) is ignored. Logic in `dashboard/plan.mjs`; in `/api/state`, `mainRuns[].plan`, `.ask` and `.recap`. Answering through the dashboard: permissions and `AskUserQuestion` under "Decisions through the dashboard"; the end-of-turn question, only with "Away from the computer" on.

`node .claude/dashboard/collect.mjs` prints the same state in the terminal (`--json` for the full JSON).

### The page itself

**Look and navigation.** A terminal look for a tool devs keep open all day: data, ids, commands and numbers in a monospace face (`--mono`: Geist Mono, JetBrains Mono, SF Mono, the system's), prose in a sans one (`--sans`); headings and borders neutral, color only for a state, always next to a glyph (✓ ✗ ● ○ ⊘). Fonts are local stacks: the dashboard loads nothing from outside, so it works offline. Themes: with nothing chosen the page follows the system (dark: `default`, light: `light`); the command palette sets `default`, `dracula`, `hacker` or `light` and turns on optional CRT effects (scanlines on cards, glow on the logo), kept per browser (`localStorage` `ai-team:theme`, `ai-team:crt`) and applied by a one-line script in each page's `<head>` before the first paint. `prefers-reduced-motion` turns every animation off.

- **Layout** (main page), after an IDE: an activity bar on the left (explorer, command palette, decisions waiting with a count, Team, Notifications), the **explorer**, the editor area with its tabs (for now only Overview, the page described below) and the **status bar** at the bottom. Explorer width, whether it is shown (`⌘B` / Ctrl+B) and the folded groups are kept per browser (`ai-team:layout`); the handle between explorer and editor drags, or moves with ← → when focused. Under 760 px the explorer is hidden (`/` shows it). The tree and the layout logic live in `shell.mjs`.
- **Explorer**: the changes and agents as a tree grouped by state (Decisions, Stuck, In progress, Blocked, Pending, Done, Ad-hoc, Agents), one line each with its glyph, `x/y` tasks, date or running clock; empty groups are left out except In progress; Done and Ad-hoc start folded. A single click opens a change or an agent as a preview tab, a double click as a kept tab (marked in the tree while open); a decision scrolls to its card. The filter on top (`/`) narrows the tree and the Changes table together, opening folded groups that match; ↑ ↓ move in the tree, ← → fold and unfold a group.
- **Tabs**: a change or an agent opens as a tab next to Overview (what used to be the drawer, now the full editor width). An open tab is focused instead of duplicated. A preview tab (italic) is replaced by the next preview; a double click, switching its view or opening one of its files keeps it. Each tab remembers its view (Conversation, Rounds, Diff), the open file, the agent filter, its scroll and expanded rows; the open tabs are kept per browser and page (`ai-team:tabs:<path>`). Alt+1 is Overview, Alt+2…8 the tabs, Alt+9 the last one, Alt+W or × or a middle click closes, Esc goes back to Overview (⌘1…9 and ⌘W belong to the browser). An **agent tab** starts with what the agent is doing now in each change it runs in (task, time, model, tokens, tools, its latest text), then its runs, newest first; the tool-by-tool output needs a server route that does not exist yet.
- **Tasks** (a change tab's sub-tab, next to Conversation, Rounds and Diff; hidden when tasks.md has no tasks): the change's tasks as one kanban. **To do**: not ticked and no running round cites it (⊘ when tasks.md marks it blocked or a dependency is not done, with what it waits for). **Doing**: a running round cites it, with the agent and its clock. **Test**: the last round on it ended but it is not ticked yet, or that round's tests came back red (red border). **Done**: ticked in tasks.md. A round cites every task in its description and the start of its prompt: `task 2.3`, `tasks 2.1–2.7` (each task of the range, in tasks.md order), `tasks 1.1, 1.2 and 1.4` (`citedTasks` in `board.mjs`, `taskIds` on each run; `taskList` on each change in `/api/state`). Each card has a badge with the task's kind, from its tasks.md section (back, front, infra, invest, test, docs, review; another section shows its first word), each kind with its own color, apart from the state colors. Clicking a card lists the rounds that cited it. The rules live in `taskBoard` (`shell.mjs`).
- **Panel** under the editor (Ctrl+` shows or hides it; height, visibility and tab kept per browser; the handle above it drags or moves with ↑ ↓). **Problems**: the decision cards first (same forms, Enter, A/D, typed text kept), then stuck changes with their `/team resume` to copy, red tests, blocked tasks and agents without a signal; a row opens its change or agent tab. A new decision opens the panel on Problems; links to the decisions (status bar, agents table) open it too. **Events**: the since-you-left timeline as one log, oldest first and newest at the bottom (it stays pinned to the bottom unless you scroll up), with a marker where the unseen part starts and "mark as seen"; already seen rows stay, dimmed. **Output**: reserved for the live output of an agent, which needs a server route. The tab counts: problems (red if something failed), new events.
- **Status bar** at the bottom: the project, then connection (live, polling, or reconnecting), decisions waiting and stuck changes (only when there are any), agents running and silent, changes in progress, estimated cost (the full totals in its tooltip), the branch of the latest team session, the time of the last change and the away switch; each count jumps to its section; cost, branch and time go below 1000 px. When `/api/state` stops answering, a strip says from when the shown state is and the page dims until the server is back.
- **Changes**: one table grouped by status (stuck, in progress, blocked, pending, latest done), with stage, `x/y` tasks, the latest test run, who is running, time, fresh tokens and cost; a stuck row carries the reason and the `/team resume <id>` with a copy button, an over-budget row is amber. **Cards** shows the previous cards; the choice is kept per browser (`ai-team:boardview`). The view switch sits in the Changes heading; the explorer's filter also hides the changes whose id does not match.
- **Command palette** (⌘K / Ctrl+K, or the search icon in the activity bar or the header; every page): open a change or an agent, copy a stuck change's `/team resume`, toggle away mode, mark "since you left" as seen, switch the changes view, go to a page, pick a theme, toggle CRT. Matching is by substring, then by subsequence (`matchScore`, `rankCommands` in `ui.mjs`).
- **Keyboard** (main page, never while typing in a field): `J`/`K` move between decision cards, change rows or cards and agent tiles; Enter opens; on a focused permission card `A` allows and `D` denies (with the typed reason); `/` filters; `?` lists the shortcuts; Esc goes back to Overview, closes the palette or clears the filter.
- **Deep links**: the open tab is in the URL (`#change=<id>`, `#agent=<name>`; "copy link" in the tab); opening such a URL opens that tab once the state arrives.

The four pages share `ui.css` (themes, header, tabs, pills, buttons, status line, key bar, command palette) and `ui.mjs` (formats: `fmtTime` HH:MM today, DD/MM HH:MM this year, with the year before that; `fmtClock` with seconds for the "updated" stamp; `fmtDur`; `ago`; `getJson`, which sends an expired outside session to `/login`; the theme, the palette and the deep links below), both served next to `feed.mjs`. The page is rebuilt on every update, but what you opened survives it: the collapsed sections (by id), the drawer's scroll, its expanded rows and "show prompt" blocks, and the text typed in a decision; the running clocks are filled by a timer, so the page's HTML does not change with the clock. Only the newest `/api/state` answer is applied when several are in flight. Everything clickable works with the keyboard (Tab, Enter or Space; Escape closes the drawer, which keeps the focus inside and gives it back on close); the presence card also opens on focus. Each decision card is a form: Enter in a text field sends the primary action, Ctrl/Cmd+Enter in the free-text answer. Wide tables scroll inside their box on a phone. The Team page asks `/api/running` (only the names of the agents running now) instead of the whole state; the hub keeps the last cards when a poll fails and says from when they are.

## Hooks

The `settings.json` created by the installer points `SubagentStart`/`SubagentStop` (dashboard) and `SessionStart`/`UserPromptExpansion` (`/team`) to `.claude/dashboard/hook.sh` (quoted in the command, so a project path with a space works), which forwards to `hook.mjs` (Node 18+) and writes `.claude/ai-team/events.jsonl` (outside git: see "What to version" in the README); with `--no-dashboard` only `hook.sh` and `hook.mjs` are copied. `events.jsonl` does not grow without limit: once it exceeds `AI_TEAM_EVENTS_MAX_BYTES` (default 1048576, 1 MiB; an invalid value means the default) the hook renames it to `events.jsonl.1` (replacing the previous generation) and starts a new file with the `TeamStart` events of each session (up to half the limit, the most recent); only one hook rotates at a time (lock `events.jsonl.lock`, created with `wx`) and no line is lost. A lock older than 30 s is considered abandoned (a hook that died) and taken over; accepted risk: two hooks taking over the same abandoned lock at the same instant may both rotate, and the second `rename` replaces the just-created `.1` generation (the damage is the one described below: exact start and end of old rounds fall back to the transcript). The dashboard and the post-compaction reminder read both generations; what is lost is the exact start and end of rounds older than two generations, which fall back to transcript timestamps. An old dashboard with a new hook reads only the current file (same loss, until the dashboard restarts). The `TeamStart` event (from `/team`, `/onboarding` or `claude --agent orchestrator`) tells the dashboard exactly which sessions belong to the team. With these events, the start and end of each round are exact even for background agents; without them, the dashboard uses transcript timestamps and considers a round with no recorded end active if it had activity within `--stale-min` (default 15 min). An Agent call that comes back with an error (`is_error`, message as text) ends there with status failed. If `settings.json` already existed, the installer adds only the missing ai-team hooks (see "Decisions through the dashboard").

**Finding node.** The desktop app runs the hooks with a short PATH (no nvm, often no Homebrew). `hook.sh` uses `AI_TEAM_NODE` when set (that binary only), else `node` on PATH, else the usual places: `~/.nvm/versions/node/*/bin`, `~/.volta/bin`, fnm's default alias, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`. With no node anywhere it exits 0 and writes `.claude/ai-team/hook-no-node` (`since`, `path`), which the dashboard shows as a warning at the top (`hooks.noNode` in `/api/state`): no events, no reminder after compaction, no notifications. The next hook that finds node removes the file. The `PermissionRequest` hook calls `node` directly (see below): without node on PATH, Claude Code reports that hook's failure itself.

**Compaction of a subagent.** Subagents compact on their own when their context fills (Claude Code writes a `compact_boundary` record in their transcript). Each team agent carries in its frontmatter a `PreCompact` hook (`hooks:` in `.claude/agents/<role>.md`, rendered from the template; it runs only while that agent is active) that calls `hook.sh compact <role>`: `hook.mjs` prints the instructions for the compaction summary (Claude Code caps them at 10 000 characters), which make the summary open with an "ai-team context" block: role and agent file to reread, change or ad-hoc slug, `tasks.md` section and markers, worktree and branch, commits and gate, open `PV-<n>`/`R<k>`/`B<n>`, the exact next step and what must not be redone. Each agent's "After compaction" section says what to reread and to continue from that step. The compaction is logged as a `Compact` event (`agent_type`, `trigger`) in `events.jsonl`. The orchestrator keeps the existing `/team` reminder (`SessionStart` with `source: compact`). Not covered by the docs, so not relied on: whether `SessionStart` fires inside a subagent and whether the agent's prompt is re-applied after its compaction.

**Agent guard.** The same `hook.sh` runs on `PreToolUse` (matcher `Bash|Edit|Write|MultiEdit|NotebookEdit`) and, inside a team subagent (`agent_type` in the hook input), `guard.mjs` refuses what the role's agent file forbids: for builder, integrator and provisioner `git add -A|--all|-u|.`, `--no-verify`, `git stash|restore|clean`, `reset --hard`, `checkout -- <path>` and a forced push; for the spec-writer the `add`/`--no-verify` part; for reviewer and validator any git subcommand that changes a repository or working tree (`show`, `log`, `diff`, `status`, `cat-file`, `branch` listings, `stash list` and `worktree list` go on) and any Write/Edit outside their own files in `openspec/changes/<id>/` (reviewer: `review-report.md`; validator: `validation-report.md` and `tasks.md`, where it marks section 3 and the state line); for every role `compose down -v|--volumes`, `docker volume rm|prune` and `find /`. The command is judged piece by piece (`&&`, `||`, `;`, `|`, newlines), so `cd x && git add -A` is refused and `git log | head` is not. The refusal goes back to the agent as `permissionDecision: deny` with the reason and the agent file to reread, and is logged as a `Guard` event in `events.jsonl`. The user's session, the `/team` orchestrator, the built-in agents and any agent outside the six roles are never judged; `AI_TEAM_GUARD=0` turns it off. It is a safety net, not a security boundary: a command wrapped in `sh -c` or a script gets past it, as it would past the prose. It is installed whenever `hook.sh` is (also with `--no-dashboard`), and `node .claude/dashboard/settings.mjs` adds it to an older `settings.json`. The reviewer has `Edit` because of it: it appends a round to `review-report.md` instead of rewriting the file and checking a `shasum`.

## Decisions through the dashboard

The `PermissionRequest` hook (`node .claude/dashboard/ask.mjs`, which the installer puts in a new `settings.json`) writes each permission request and each `AskUserQuestion` to `.claude/ai-team/pending/` and waits for the answer. The dashboard shows "Decisions waiting for you" in the Problems tab of the bottom panel: the command (or file) with **Allow once** / **Deny** (with a reason, which goes back to Claude), and the questions with their options, multi-select and free-text "Other". The app shows its own dialog at the same time and the first answer wins; once answered in the app (the transcript gets the `tool_result`), the pending item disappears. With no answer, the hook gives up after `AI_TEAM_ASK_WAIT_S` (default 280 s) and only the app remains; with **away from the computer** on, it waits `AI_TEAM_AWAY_WAIT_S` (default 3300 s, ~55 min). The hook `timeout` is 3600; a project installed with 300 is adjusted by `node .claude/dashboard/settings.mjs`. The question also appears on the session card, read-only: while the hook waits, the card points to "Decisions waiting for you"; afterwards, it says the dashboard is no longer waiting and the answer goes in the session. A background subagent has no dialog: the dashboard is the only place to approve. `AI_TEAM_ASK=0` disables it. Routes: `pending` in `/api/state` and `POST /api/answer` (`{ id, behavior: allow|deny, message?, answers? }`, JSON only and same origin). Since the dashboard approves commands, access from outside the machine requires a token (see "Access from outside the machine"). Project with an existing `settings.json`: the installer adds only the missing ai-team hooks (`dashboard/settings.mjs`, with a copy in `settings.json.bak-ai-team`; the rest of the file stays the same). To do this without reinstalling: `node .claude/dashboard/settings.mjs` (`--dry-run` shows it first). If the JSON has comments, it does not write and shows the snippet; the `PermissionRequest` one is

```json
"PermissionRequest": [{ "hooks": [{ "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR/.claude/dashboard/ask.mjs\"", "timeout": 3600 }] }]
```

## Away from the computer

The app's end-of-turn question (the box with buttons) is neither a permission nor an `AskUserQuestion`: answering it means sending a message to the session, which no hook does after the turn has ended. That is why the dashboard only shows it ("answer in the session") and the phone gets "question for you" with the question and the options. To answer through the dashboard, turn on **away from the computer** in the header (`.claude/ai-team/away.json`, per project): when the turn is about to end with a question, the `Stop` hook (`timeout` 3600) holds the end of the turn and waits up to `AI_TEAM_AWAY_WAIT_S` (default 3300 s); the dashboard shows the options, a text field and **Leave it to the app**, and the answer comes back as `{"decision":"block","reason":…}`, which Claude treats as your answer (the app records it as "Stop hook feedback"). While it waits, the app shows the session running, without its buttons; with no answer, or with the mode turned off midway, the turn ends and the question appears in the app. Route: `GET/POST /api/away`.

**Proposal approval.** The orchestrator asks it with `AskUserQuestion` (`Approve` / `Changes`, the text of the changes through "Other"), so it is a pending item like any other: the dashboard and the phone catch it without away mode, in the desktop app and in a terminal session alike. The wait is the usual 280 s (`AI_TEAM_ASK_WAIT_S`); for longer, turn on away mode.

## Phone notifications (ntfy)

With `~/.config/ai-team/notify.json`, the hooks notify through the [ntfy](https://ntfy.sh) app: new decision (permission or question, the same as in the dashboard), agent finished (`SubagentStop`, with the start of its summary), session that ended its turn and waits for you (`Stop`), turn stopped by an error (`StopFailure`: usage limit, overloaded API, login failure…) and session closed (`SessionEnd`: `/clear`, `/resume`, logout, exit; the hook has `timeout` 10 because Claude Code's default is 1.5 s). Interrupting with Esc or the stop button sends nothing: Claude Code has no hook for that (`Stop` does not run in that case). Old configs get the new events turned on (`eventsVersion`). Without the file, nothing is sent. To start:

```bash
node .claude/dashboard/notify.mjs setup      # creates the file with a random topic and explains how to subscribe on the phone
node .claude/dashboard/notify.mjs test       # sends a test notification
```

**Buttons.** With `dashboardUrl` set (Notifications page; the address the phone reaches, e.g. the Tailscale one, or the project page `.../p/<name>/` in a hub), a decision notification carries [ntfy action buttons](https://docs.ntfy.sh/publish/#action-buttons): **Allow** / **Deny** for a permission, one per option for a single question with exactly two options (the proposal approval, a yes/no end-of-turn question in away mode), and always **Open**, which opens the dashboard. Anything else (three or more options, multi-select, several questions, free text) gets only **Open**: the dashboard is the better place for it. The answer buttons `POST <dashboardUrl>/api/answer` with the item's one-time `secret` (written by `ask.mjs` in the pending file, never listed by `/api/state`): that route is reachable from outside without login, but only answers the item whose secret it carries, once (`already answered` afterwards); the dashboard token never travels through ntfy. With `detail: false` the body would carry the question text, so only **Open** goes. On a public ntfy.sh topic without a token, whoever guesses the topic could tap the buttons: use a token or your own server before turning the buttons on (same advice as for the message content).

The installer handles this: if the PC has no config yet, it asks for the topic (enter skips, `new` generates one) and offers to send a test; without a terminal, use `install.sh --ntfy-topic <topic>` (on a PC already configured, it only changes the topic). It can also be configured from the dashboard's **Notifications** page (`/notifications`): topic, server, token (never shown back), events, content, dashboard address, events from that project only (or a muted project) and a test button. The config belongs to the PC (applies to all projects); the hooks that fire live in each project's `settings.json`. In the file: `ntfy.server`/`topic`/`token` (own server or ntfy.sh with a token), `on` (`decision`, `agent_stop`, `turn_stop`), `detail` (`false` sends only the title, with no command or agent text; public ntfy.sh is open to anyone who knows the topic) and `dashboardUrl` (opened when the notification is tapped). `AI_TEAM_NOTIFY=0` disables it. Sending runs in the background and never holds the hook. Whatever `detail` says, bearer tokens, `key=value` secrets (token, password, api key…), `--token x` arguments, credentials in URLs and known key shapes (AWS, GitHub, Slack, OpenAI-style) are blanked before anything leaves the machine (`redact` in `notify.mjs`). A new config made by `setup` starts with `detail: false` (public ntfy.sh with no token: anyone who guesses the topic reads it; the Notifications page warns when the content is on in that situation) and `quietAtComputer: true`: "agent finished" and "session waiting for you" only go out with the dashboard's "away from the computer" mode on in that project; decisions, errors and session end always go. An existing config keeps its behaviour until changed on the page. When the away-mode wait runs out, the phone gets "the dashboard is no longer waiting" and the question is in the app; the turn that goes on after an answer does not ask the same question again. On the Notifications page reached from outside (Tailscale, a tunnel), the dashboard address is suggested from the one in use. A new `settings.json` comes with the `Stop`, `StopFailure` and `SessionEnd` hooks; in an existing one, the installer adds the missing ones.

## Access from outside the machine

The dashboard stays on `127.0.0.1`, open to whoever is on the machine. A request that arrives through a proxy (`X-Forwarded-For`), with another `Host` or from another interface only gets in with the token: a cookie after `/login` (30 days, `HttpOnly`, `SameSite=Strict`, `Secure` behind HTTPS) or `Authorization: Bearer`. Without a token, outside access is refused. The token lives in `~/.config/ai-team/token` (or `AI_TEAM_TOKEN`); create it with `node .claude/dashboard/auth.mjs token` and restart the dashboard. To open it on the phone, the recommended path is **Tailscale Serve** (HTTPS only inside your tailnet, no open port):

```bash
node .claude/dashboard/auth.mjs token          # once per machine
node .claude/dashboard/server.mjs              # or --hub
tailscale serve --bg 4321                      # https://<machine>.<tailnet>.ts.net/ → 127.0.0.1:4321
```

On the phone, with the Tailscale app on, open the `ts.net` address, paste the token and you're done. Put that address in `dashboardUrl` in `notify.json` so the notification opens the dashboard (the Notifications page suggests it when opened from there). Do not use `tailscale funnel` (public on the internet). Alternative with your own domain: Cloudflare Tunnel + Cloudflare Access.

## Running it

`node .claude/dashboard/server.mjs --help` prints the flags; `--version` the copy's version (also at startup and in `GET /api/health`, which answers `{ ok, version, mode, projectDir | hubFile, uptimeS, pid }` without reading any transcript: the probe for a supervisor). An unknown flag stops the server with the usage, instead of starting it on the wrong project. `--port 0` takes a free port and prints the one bound. `AI_TEAM_LOG=silent` prints nothing, `debug` logs every request.

**As a service (macOS, launchd)**, so the phone flow does not depend on a terminal staying open: `~/Library/LaunchAgents/eu.ai-team.dashboard.plist` with `ProgramArguments` = `[/path/to/node, /path/to/project/.claude/dashboard/server.mjs]` (or `--hub`), `RunAtLoad` and `KeepAlive` true, `StandardOutPath`/`StandardErrorPath` to a log file, then `launchctl load ~/Library/LaunchAgents/eu.ai-team.dashboard.plist`. On Linux, a user `systemd` unit with `ExecStart=/usr/bin/node .../server.mjs`, `Restart=on-failure` and `WantedBy=default.target` (`systemctl --user enable --now ai-team-dashboard`). Give the service the same `HOME` as the user so it finds `~/.claude` and `~/.config/ai-team`.

**Updating an installed copy.** `.claude/dashboard/` is code, never edited by hand, so a new `install.sh` run (from the clone: `./install.sh .` or `make install TARGET=…`) replaces the files that changed without `--force` ("updated" in the log); only a profile's `cycle.html` keeps the `--force` rule. `--force` is still what overwrites hand-edited generated Markdown. Compare `node .claude/dashboard/server.mjs --version` with the clone's `dashboard/version.mjs` to know whether a project is behind. The installer also adds `.claude/ai-team/` to the project's `.gitignore` when it is a git repository (hook log, pending decisions and answers, which carry tool inputs).

### Variables

| variable | default | where |
|---|---|---|
| `PORT` | 4321 | server: listening port (`--port` wins) |
| `AI_TEAM_PROJECT` | current folder | server: the project to serve (`--project` wins) |
| `AI_TEAM_STALE_MIN` | 15 | server: minutes without transcript activity before "no signal" (`--stale-min` wins) |
| `AI_TEAM_IDLE_MS` | 60000 | hub: how long a project's live context stays after its last tab |
| `AI_TEAM_HUB` | `~/.config/ai-team/hub.json` | hub registry (`--hub FILE` wins) |
| `AI_TEAM_LOG` | `info` | server: `silent`, `info` or `debug` |
| `AI_TEAM_TOKEN` | — | token for access from outside (instead of the file) |
| `AI_TEAM_TOKEN_FILE` | `~/.config/ai-team/token` | where the token lives |
| `AI_TEAM_NOTIFY` | — | `0` turns the phone notifications off |
| `AI_TEAM_NOTIFY_FILE` | `~/.config/ai-team/notify.json` | the ntfy config |
| `AI_TEAM_ASK` | — | `0` turns the decisions through the dashboard off |
| `AI_TEAM_ASK_WAIT_S` | 280 | how long the hook waits for an answer |
| `AI_TEAM_AWAY_WAIT_S` | 3300 | the same with away mode on |
| `AI_TEAM_EVENTS_MAX_BYTES` | 1048576 | hook: size that rotates `events.jsonl` |
| `AI_TEAM_NODE` | — | hook.sh: the node binary to use (only that one) |

The tests set `AI_TEAM_NOTIFY_FILE`, `AI_TEAM_TOKEN_FILE` and `AI_TEAM_HUB` to files under their temp folder so they never touch the machine's config (`tests/run.sh`; `make test-node T=<name>` does the same for one file).

## Team page

This is the dashboard's "Team" tab; not to be confused with the `/team` skill, which calls the team into a session. `dashboard/team.html` builds the page in the browser from the installed project and is the second tab in the header (the "Team" link always appears). It shows: (1) the **team**, read from `<project>/.claude/agents/*.md` (frontmatter `name`, `description`, `model`, `tools`; link to `/agents/<name>.md`; green dot on agents running now; "no frontmatter" when missing); (2) **how to call the team**: fixed agent in `settings.json`, or `/team` and `claude --agent orchestrator`, with a warning when the hooks that keep the role after compaction are missing; (3) the **project context**, from `.claude/ai-team.conf`, including the hub team; (4) the **cycle of a change**, with the ad-hoc task. Updates over SSE like the dashboard. Routes: `/team` (HTML), `/api/team` (JSON `{project, agents, context, entry, hasConf}`, read-only; `entry` carries only `fixedAgent` and skill and hook booleans) and `/agents/<name>.md` (only `[a-z0-9-]+`). Without `ai-team.conf` or without agents, the page opens anyway (uses the folder name and says there are no agents).

Exposed conf keys (closed list in `dashboard/team.mjs`; `GIT_REMOTE`, `TEST_PERSONAS` and the rest are not exposed): `PROJECT_NAME`, `PROJECT_DESCRIPTION`, `LAYOUT`, `HAS_OPENSPEC`, `CI`, `HUB_TEAM`, `GIT_DEFAULT_BRANCH`, `GIT_WORK_BRANCH`, `GIT_PROTECTED_BRANCHES`, `BACKEND_`/`FRONTEND_` + `DIR`, `STACK`, `BRANCH`, `PROTECTED_BRANCH`, plus `BACKEND_GATE`/`FRONTEND_GATE` (the `*_CMD_LINT/FORMAT/TYPECHECK/TEST/BUILD` joined by `; `, as the installer does) and `DOCS_CONTEXT`, `DOCS_STANDARDS`, `DOCS_ENV`.

### Cycle per profile

The "cycle of a change" part comes from `dashboard/cycle-default.html` (generic text: spec, build per section, gate, review, validation, integration). A profile replaces only that part with `profiles/<profile>/dashboard/cycle.html`: an HTML fragment (may have `<style>` and `<script>`), which the installer copies to `.claude/dashboard/` and the server inserts in place of the page's `<!--ai-team:cycle-->` marker. Without `cycle.html`, the default applies. In projects with an old profile copy of the team page (`equipe.html`), run `install.sh --profile <profile> --force` to replace it with the generic version (the installer does not overwrite without `--force`).
